# R0.4.2-B — Formal Scenario on StressEngine (engine-facing)

Status: **COMPLETE pending review** (2026-09-09)  
Owner: Stress & Scenario Engineer  
Related: RF-004 (stays IN PROGRESS), RF-011, milestone § R0.4.2

## Goal

Make engine-facing stress accept formal `Scenario` as first-class input so
formal HTTP does not need to collapse wire → `StressScenario` before apply.

## What changed

- `StressEngine.run` / `evaluate` and `ScenarioComparisonEngine.compare` take
  `Sequence[ScenarioLike]` (`Scenario | StressScenario`).
- Evaluate metadata (`id` / `kind` / `max_loss_pct`) normalized via
  `_evaluation_fields` (`category_to_kind` for formal).
- `PortfolioService.stresses` / `threat_evaluation` (and dashboard batch types)
  accept `ScenarioLike`.
- Formal HTTP `POST /risk/stress/formal/custom` and
  `.../formal/evaluate/custom` use `wires_to_scenarios` → domain `Scenario` →
  engine (no `wires_to_stress` on that path).
- `ScenarioAttributionEngine` applies formal / isolated factor `Scenario`
  objects directly through `apply_scenario` (removed apply-path
  `scenario_to_stress` collapse).
- `wire_to_stress` / `wires_to_stress` retained as adapters for tests and
  migration helpers.

## Explicitly unchanged

- Legacy `/api/v1/risk/stress/*` StressScenario wire endpoints.
- Default scenario libraries still shipped as StressScenario on the wire
  (`GET /stress/scenarios`); formal list remains a projection.
- RF-004 / RF-011 not closed.
- Shock unit conventions unchanged.

## Remaining for full R0.4.2 converge

- Prefer formal HTTP as the default client path (frontend / OpenAPI examples).
- Retire dual list endpoints once clients migrate
  (`/stress/scenarios` vs `/scenarios/formal`).
- Any remaining callers that still build StressScenario-only payloads for
  compare/what-if can migrate at leisure; engine already accepts both.
