## Summary
`PortfolioRepository` now distinguishes identity-safe writes: `create` fails if the id exists (`PortfolioAlreadyExists`), `update` fails if the id is missing (`PortfolioNotFound`). Both are `ValueError` subclasses, so any HTTP wiring through `http_bad_request` maps to 400 `Invalid request`. `save` remains a legacy upsert because seed/callers outside this slice still use it (`wiring.py` and uneditable tests).

`RiskRunWorker.submit` no longer upserts. With a SQLAlchemy session factory it create-if-absents; if the id is already stored it **attaches the stored book** and does not replace positions, name, or desk. A second submit with the same client id therefore cannot wipe trades. In-memory / inline demo calculate (no `session_factory`) is unchanged. No portfolio HTTP create/update routes were added; tests hit the repo and worker. No VaR numbers or `models.py` changes. RF-009 stays open for R0.8.4 typed requests. RF-013 stays open (canonical versioned IDs, HTTP identity, Postgres identity coverage in R0.8.5).

## Known limitations / risks
- RF-009 remains **open**. This slice stops submit from upserting a client id over a stored book; it does not close reproducibility (typed requests / same-spec interactive vs worker still remain).
- RF-013 remains **open**. Create vs update is real on the repo, but HTTP identity is still the live risk-run payload, `save` is still an upsert for legacy callers, and IDs are not yet server-issued or versioned.
- Callers outside this slice (`wiring.py` seed, other tests) still call `save` and can overwrite. New write paths must use `create` / `update`.
- Attaching the stored book silently ignores a posted book that differs from storage. That is intentional for “calculate persisted portfolio”; a fail-closed mismatch 400 is left for typed requests (R0.8.4) if product wants it.
- No in-memory `PortfolioRepository` (none existed). No HTTP portfolio create/update.
