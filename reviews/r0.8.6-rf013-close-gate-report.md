## Why CLOSE (not IN PROGRESS)

The original attack (SEC-003) is: POST a run whose `portfolio.id` equals the seed id with a distinct trade set; `GET /portfolio` / SQL `portfolios.id = global-macro` must remain the Cross-Asset seed. That pin now exists on HTTP, not only on a generic worker id.

R0.8.3 left RF-013 open specifically for HTTP identity + Postgres coverage + versioned IDs. Postgres landed in R0.8.5. HTTP `global-macro` is this slice. Versioned/server-issued IDs were never an acceptance cell; they stay named residuals.

Would this gate defend CLOSE to a second reviewer? **Yes**, provided `portfolio_version` / leftover `save` / ACLs stay residuals and are not relabeled MET.

## P1 residuals (not blocking close)

1. **No `portfolio_version` / server-issued ids.** First persist submit is still create-if-absent with a client-chosen id.
2. **Legacy `save` upsert** remains for seed (`wiring.py`) and older tests. New write paths must use `create` / `update`. Submit does not call `save`.
3. **Object ACLs / IAM** — RF-014. Out of scope.
4. **Attach silently ignores** a posted book that differs from storage (not HTTP 409). Intentional for “calculate persisted portfolio”.
5. **SQLAlchemy trade reload does not preserve insert order.** Identity pin is id-set + economics; catalog GET keeps SAMPLE order.
