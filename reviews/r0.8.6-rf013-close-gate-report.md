## Why IN PROGRESS (not CLOSE)

The original attack (SEC-003) is pinned on HTTP: POST a run whose `portfolio.id` equals the seed id with a distinct trade set; `GET /portfolio` / SQL `portfolios.id = global-macro` remains the Cross-Asset seed. That pin stays.

R0.8.3 left RF-013 open for HTTP identity + Postgres coverage + versioned IDs. Postgres landed in R0.8.5. HTTP `global-macro` is this slice. Versioned/server-issued IDs, live full-book calculate, leftover `save`, and PERF-016 unconstrained `risk_results.payload` are still open. Rubber-stamping CLOSE after the HTTP pin would treat those as MET.

Would this gate defend CLOSE to a second reviewer? **No.**

## Residuals (keep IN PROGRESS)

1. **No `portfolio_version` / server-issued ids.** First persist submit is still create-if-absent with a client-chosen id.
2. **Live calculate still POSTs a full book.** Persistence is still a parallel path, not canonical for production-style runs.
3. **Legacy `save` upsert** remains for seed (`wiring.py`) and older tests. New write paths must use `create` / `update`. Submit does not call `save`.
4. **Object ACLs / IAM** — RF-014. Out of scope.
5. **Attach silently ignores** a posted book that differs from storage (not HTTP 409). Intentional for “calculate persisted portfolio”.
6. **SQLAlchemy trade reload does not preserve insert order.** Identity pin is id-set + economics; catalog GET keeps SAMPLE order.
7. **PERF-016 / cell 4 UNMET.** `risk_results.payload` unconstrained JSON; no structured/reference model for derived results.
