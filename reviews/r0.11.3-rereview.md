## Verdict: REVISE

Finding 1 is closed on the live what-if route. Finding 3 is closed.
Finding 2 is **not** closed on the path a client actually hits.

The new `request.stream()` running total works when `enforce_workload_limits`
is invoked on a raw Starlette `Request`. That is what the new ASGI unit test
drives. It is not what happens on `POST /api/v1/market/snapshot` (or any
other typed-body route). FastAPI reads the body for Pydantic first. With no
`Content-Length`, every ASGI chunk is delivered and retained; the cap then
either 413s on the already-buffered bytes (valid JSON) or never runs and
the request 422s (invalid JSON). A streaming reject would have stopped after
the first oversize chunk and would not have kept the tail.

Finding 2 was Important against SEC-002 / CWE-770. It still is. Remaining
Critical/Important on items 1–3 is not 0.

## Findings (items 1–3 only)

### 1. CLOSED — What-if `add` no longer bypasses the position cap

- Files: `backend/app/api/workload.py` (`enforce_parsed_payload`,
  `_add_with_position_count`, `_positions_for_changes`)
- What changed: for an object that has a `changes` list, computed size is
  `len(sibling-or-portfolio.positions) + count(add with a position object)`.
  Over `max_positions` → 413 `field=positions`.
- Independent probe (`QUANTLINEAGE_MAX_POSITIONS=2`):

  | Probe | Result |
  |---|---|
  | `POST /api/v1/risk/what-if` 1 equity + 3 adds | **413** `actual=4`, no `after` |
  | `POST /risk/what-if` same | **413** `actual=4` |
  | 1 + 1 add (at cap) | **200** `after.market_value=200` |
  | 2 + 1 add | **413** `actual=3` |
  | empty book + 3 adds | **413** `actual=3` |
  | sibling `positions: []` decoy + book of 1 + 3 adds | **413** `actual=3` |
  | omitted `portfolio.positions` + 3 adds | **422** (Pydantic), not a 4-position book |
  | `operation: ADD` | **422**, not a 4-position book |

- Leftover bypasses on this item: **none** that restore a computed book
  over the cap. `modify`/`remove` do not grow `len(positions)`. A missing
  `positions` key skips the computed check but fails Portfolio validation
  before risk. Finding 4 (summing two named `positions` lists) is unchanged
  and still deferred.

### 2. STILL VALID — Important — Live missing-`Content-Length` path still buffers the full stream

- Files: `backend/app/api/workload.py` (`_read_body_capped`,
  `enforce_workload_limits`);
  `backend/tests/test_workload_limits.py`
  (`test_chunked_body_without_content_length_stops_before_full_buffer`)
- What's wrong: the running-total abort is real in isolation and dead on
  the app. FastAPI solves the Pydantic body parameter by reading the ASGI
  stream to completion **before** `_read_body_capped` iterates (and, for
  invalid JSON, before the dependency runs at all). `_read_body_capped`
  then sees one already-joined blob (`actual` equals the full offered
  size) or is never called. `request._body` / the receive log retain the
  tail.

  | Probe | Receive log | Status | `_read_body_capped` |
  |---|---|---|---|
  | Isolated `Request`, no CL, 80+80+80+5, cap 64 | `[(80, True)]` (80 B) | **413** `actual=80`, no cached `_body` | ran, stopped |
  | Bare app, **no** body param, same chunks | `[(80, True)]` | **413** `actual=80` | ran, stopped |
  | Bare app, **Pydantic body**, same chunks | five events, **245 B** | **422** JSON | **never called** |
  | Live `POST /api/v1/market/snapshot`, no CL, `xxxx` chunks | five events, **245 B** | **422** `validation_error` | **never called** |
  | Live same path, chunked **valid** JSON, 270 B, cap 64 | five events, **270 B** | **413** `actual=270` | ran **after** full drain |
  | Live declared `Content-Length: 999999`, no body | `[(0, False)]` | **413** `actual=999999` | not needed |

  `BaseHTTPMiddleware` alone is not the defect: a no-op wrapper still 413s
  after 80 bytes on a route with no body model. Adding a typed body is
  enough to replay the original hole, with or without
  `LegacyDeprecationMiddleware`.

- Why it matters: SEC-002 is memory/availability. Omitting `Content-Length`
  (chunked HTTP/1.1, raw ASGI) is the attack the byte cap exists to stop.
  On every production POST that takes a Pydantic body — snapshot, what-if,
  VaR, stress, limits, runs — that attack still delivers the entire stream
  into process memory. Tightening `QUANTLINEAGE_MAX_REQUEST_BYTES` does not
  bound RSS for this client. Invalid JSON is worse: no 413 at all.

  The new test documents the gap and then avoids it: “Full-app ASGI through
  `BaseHTTPMiddleware` can replay an empty body; the chunked test drives
  `enforce_workload_limits` with a raw `Request`.” That isolated call is
  not the live path. The test would stay green if `_read_body_capped` were
  never reached from `app`.

- Suggested fix: enforce the byte cap **in front of** FastAPI body parsing,
  on the ASGI stream itself (pure ASGI middleware, or Starlette
  `max_body_size` / `RequestBodyLimitMiddleware`), not only inside a
  FastAPI `Depends`. Keep the `Content-Length` pre-check. Add a **full-app**
  ASGI test (typed-body route, no `Content-Length`, 80-byte chunks, cap 64)
  that fails if more than the first oversize chunk is received. Do not
  accept a test that constructs `Request` by hand.

### 3. CLOSED — Deep JSON under the byte cap is not 500

- File: `backend/app/api/workload.py` (`_iter_dicts`, `MAX_JSON_DEPTH=64`)
- Independent probe: 1200-deep `{"a":...}` (8402 bytes < 1 MiB) on
  `POST /api/v1/market/snapshot` with `raise_server_exceptions=False` →
  **413** `{code: payload_too_large, field: nesting, limit: 64, actual: 65}`.
  50-deep control → **422**, not 500.
- Leftover on this item: none for the stated check. Depth 64 is a code
  constant (implementer-noted); not a 500.
