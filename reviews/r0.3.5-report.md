## Summary

In-process QuantLib is already serialized by `_QL_PROCESS_LOCK` (R0.3.2). R0.3.5 pins the complementary process partition:

- Compose `worker` (`python -m app.worker`) is a distinct OS process from Compose `backend`.
- Compose `backend` sets `QUANTLINEAGE_EXTERNAL_WORKER=1` so the API process enqueues only.
- Additional worker replicas are the supported parallel full-revaluation scale-out (Postgres `SKIP LOCKED`).
- `RiskRunWorker`'s `ThreadPoolExecutor` schedules jobs only. QuantLib calls from those threads still take `_QL_PROCESS_LOCK`.
- `full_revaluation_pnl_series` stays a sequential `PricingEngine` loop. No in-process QuantLib thread pool was added.
- Native C/C++ sources contain no QuantLib.
- A detector fails if someone starts a `ThreadPoolExecutor` / `ProcessPoolExecutor` that references QuantLib / `ql.Settings` without `_QL_PROCESS_LOCK` / `_session`.

No job platform. No QuantLib in C++. No numerical methodology change.

Two sibling OS processes can hold different QuantLib evaluation dates at the same time.

## Known limitations / risks

- There is still no in-process scenario-block process pool. Horizontal QL scale-out is Compose worker replicas, not `ProcessPoolExecutor` inside `full_revaluation_pnl_series`.
- In-process job threads remain a serial QuantLib bottleneck under `_QL_PROCESS_LOCK`. That is intentional.
- `MarketSnapshot.as_of` is still an unconstrained string (R0.3.1).
- The unlocked-pool detector is a source contract: it flags a pool that also names QuantLib / `ql.Settings` without `_QL_PROCESS_LOCK` / `_session`. A pool in file A that calls an unlocked QL helper in file B would not be seen unless that helper itself is scanned as a pool.
