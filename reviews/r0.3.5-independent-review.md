## Verdict: APPROVE

There is no leftover on-disk in-process QuantLib fan-out that mutates `Settings` / builds engines off `_QL_PROCESS_LOCK`. `full_revaluation_pnl_series` is still a sequential `PricingEngine` loop. Native C/C++ sources do not reference QuantLib. Compose `worker` is a distinct service (`python -m app.worker`) from `backend` (`uvicorn app.main:app`); `QUANTLINEAGE_EXTERNAL_WORKER=1` is set only on the API service.

This slice’s production edits are docstrings and comments on a partition that already existed. The new executable artifact is `backend/tests/test_quantlib_process_parallelism.py`. Two of those tests actually exercise QuantLib (sibling OS processes; job-style thread pool through `value()`). The unlocked-pool detector is **not** a closed contract: several realistic QuantLib thread pools pass it, including an unlocked `ql.Settings` write appended to `risk_run_worker.py` (the docstring this slice added already names both `ql.Settings` and `_QL_PROCESS_LOCK`).

## Findings

### 1. VALID — Important — Unlocked-pool detector is a substring pin, not a lock

- Files: `backend/tests/test_quantlib_process_parallelism.py:80-112`,
  `backend/app/services/risk_run_worker.py:1-15`
- What's wrong: A file is a violation only when it (1) names `ThreadPoolExecutor` /
  `ProcessPoolExecutor`, (2) matches `\bQuantLib\b|\bql\.Settings\b`, and (3) does
  **not** match `_QL_PROCESS_LOCK|\._session\b|_session\(`. That is not “takes the
  process lock.” In-memory probes (no checkout writes):

  | Shape | Detector |
  |---|---|
  | `ThreadPoolExecutor` + `engine.value()` (no QL token in that file) | `[]` |
  | Current `risk_run_worker.py` plus an unlocked `ql.Settings` write | `[]` |
  | QL pool whose only lock text is a comment `# take _QL_PROCESS_LOCK` | `[]` |
  | QL pool plus an unused `def _session():` | `[]` |
  | QL pool under a **private** `RLock()` named `_QL_PROCESS_LOCK` | `[]` (this is the slice’s own “safe” fixture) |

  This slice’s new `risk_run_worker` docstring contains both `ql.Settings` and
  `_QL_PROCESS_LOCK`, so the live tree scan cannot fail that file even if unlocked
  QuantLib is added later. `test_risk_run_worker_job_pool_does_not_import_quantlib`
  only walks `ast.Import` / `ast.ImportFrom`; `importlib.import_module("QuantLib")`
  would not be seen.
- Why it matters: The report sells the detector as the regression that “fails if
  someone starts a thread/process pool that references QuantLib without the
  process lock.” It fails only the synthetic same-file fixture. A scenario-level
  `ThreadPoolExecutor` around `PricingEngine.value` — the exact in-process QL
  fan-out R0.3.5 forbids — would stay green. Cross-file weakness is mentioned in
  the implementer report; the docstring pre-clear and comment/`_session(` /
  private-lock cases are not.
- Suggested fix: Do not treat this detector as closing the in-process fan-out
  contract. If a pin is required, fail on any `app/` pool that reaches
  `QuantLibPricingEngine` / `ql.Settings` unless the **same** `_QL_PROCESS_LOCK`
  object is acquired (import-time identity or AST of `with _QL_PROCESS_LOCK` /
  `with self._session`). Keep the existing `value()` lock test. This is a pin
  quality issue, not a current production race.

### 2. VALID — Important — “API process stays off QuantLib” overclaims the flag

- Files: `docs/adr/007-quantlib-concurrency.md:72-73`,
  `docker-compose.yml:35-36`,
  `backend/app/api/risk.py` (sync `def risk_summary` / `risk_var` / …),
  `backend/app/api/deps.py:40-43`
- What's wrong: `QUANTLINEAGE_EXTERNAL_WORKER=1` only stops `RiskRunWorker.submit`
  from `_schedule`ing. Compose `backend` still imports
  `create_pricing_engine()` at process start and prices on request threads.
  Starlette runs those sync handlers on its own thread pool. That is in-process
  QuantLib, serialized by `_QL_PROCESS_LOCK` (R0.3.2), not process-partitioned
  off the API.
- Why it matters: The ADR table cell “API process stays off the QL work” and the
  Compose line “do not run QuantLib in the API process” are false for the default
  HTTP risk path. The real partition is **risk-run jobs**, not all valuation.
  Two concurrent `/risk/summary` requests are still one QuantLib address space.
- Suggested fix: Narrow the wording to “Compose API enqueues risk-run jobs;
  `python -m app.worker` executes those jobs in another OS process. Sync HTTP
  valuation still runs in the API process under `_QL_PROCESS_LOCK`.” Do not
  claim the API is QuantLib-free.

### 3. VALID — Minor — Product process partition is not runtime-tested

- Files: `backend/tests/test_quantlib_process_parallelism.py:180-205`,
  `backend/tests/test_quantlib_process_parallelism.py:219-255`
- What's wrong: Compose isolation is asserted by reading `docker-compose.yml`
  text. `test_worker_module_is_not_the_api_process` asserts different files,
  `hasattr(worker, "app")`, and `"python -m app.worker" in worker.__doc__`.
  The only live two-process test uses raw `python -c` + `import QuantLib`, not
  `app.worker` / `QuantLibPricingEngine` / two claimed risk runs.
- Why it matters: OS processes isolating `Settings` is a QuantLib/runtime
  property. It does not prove QuantLineage’s Compose backend+worker pair actually
  partitions work. A later compose edit that ran `app.worker` inside the API
  command would be caught by the YAML pin; a wiring bug that priced queued runs
  in the API process despite the env flag would not.
- Suggested fix: Optional later pin (not required to APPROVE this slice): one
  durable-worker test that API `submit(execute=None)` with
  `QUANTLINEAGE_EXTERNAL_WORKER=1` does not enter `_session`, while
  `poll_once` on a second `RiskRunWorker` does. Existing
  `test_durable_worker.py` already covers enqueue-vs-poll; it does not read
  QuantLib Settings.

### 4. VALID — Minor — Full-reval “no executor” pin is function-local

- File: `backend/tests/test_quantlib_process_parallelism.py:170-177`
- What's wrong: Only `inspect.getsource(full_revaluation_pnl_series)` is scanned.
  A helper used by that function, or the ES full-reval loop in `es.py`, could
  grow a pool without failing this test. The live `app/` detector would still
  miss a helper that calls `engine.value()` (Finding 1).
- Why it matters: The named pin matches today’s sequential body. It is not a
  historical-full-reval fan-out guard.
- Suggested fix: Accept as a narrow source pin. Do not cite it as proof that
  historical full reval cannot grow threads.

## Leftover bypasses (process-partition / in-process QL fan-out)

1. **Current production fan-out:** none found. The only app-owned
   `ThreadPoolExecutor` is the risk-run job scheduler; QuantLib construction and
   `Settings` writes stay inside `_session` / `_QL_PROCESS_LOCK`. Full reval is
   sequential. Native stays QuantLib-free. No `ProcessPoolExecutor`.
2. **Pin leftover (must not be treated as a closed guard):** the unlocked-pool
   detector would still pass a new in-process QuantLib thread pool (Finding 1).
   That is a future bypass of the *claimed* regression, not a race on today’s
   tree.
3. **Process-partition leftover vs written claim:** `QUANTLINEAGE_EXTERNAL_WORKER`
   partitions **queued risk-run jobs**, not all QuantLib. Sync HTTP valuation
   remains in the API process (Finding 2). Two worker replicas (or two OS
   processes) are still the supported parallel full-reval scale-out; one worker
   with `max_workers=2` is still a serial QL bottleneck under the process lock.
