# R0.1 Independent Quant/QA Review

## Verdict: REVISE

The core hand numbers are correct, and the focused suite passes, but the safety net does not yet meet the stated mutation/concurrency bar. In particular, it does not exercise the demonstrated cross-instance QuantLib race, and it does not pin `HistoricalRiskEngine`'s ES threshold membership.

## Independent recomputation

I recomputed cases A–G without calling `numpy.quantile`, using the documented linear rule `q * (n - 1)` and direct interpolation:

- A: VaR95 `19.05`, VaR99 `19.81`, ES95/99 `20.0`
- B: VaR95/99 and ES95/99 `0.0`
- C: VaR95/99 and ES95/99 `0.0`
- D: VaR95 `17.0`, VaR99 `19.4`, ES95/99 `20.0`
- E: VaR95/99 and ES95/99 `10.0`
- F: VaR95 `95.05`, VaR99 `99.01`, ES95/99 `100.0`
- G: VaR95 `3.85`, VaR99 `3.97`, ES95/99 `4.0`
- Gamma: `0.5 * 40 * 0.10^2 = 0.2`

All literal goldens match the independent calculations.

The unit-equity path is valid: `BuiltinPricingEngine` returns cash delta `quantity * spot = 1`, with gamma, vega, DV01, and FX delta zero; LINEAR P&L therefore equals the supplied equity-return series.

## Findings

### 1. VALID — Important — QuantLib race is documented structurally but not tested

- File: `backend/tests/test_quantlib_process_state.py`
- What's wrong: The tests show that locks differ and that sequential sessions write different global dates, but never overlap two sessions. They therefore do not prove serialization is unsafe or expose the actual race required by R0.1.5.
- Why it matters: I ran a deterministic two-thread/event probe. While engine A's session expected 2020, engine B changed the shared date to 2024; when A exited, B observed the restored wall-clock date instead of 2024. The current tests pass despite this real contamination.
- Suggested fix: Add a deterministic event-controlled overlap test using two engine instances. Assert that A observes B's evaluation date while both sessions are active and/or that one session's restore clobbers the other's date. Mark it explicitly as the current known unsafe behavior pending R0.3.

### 2. VALID — Important — HistoricalRiskEngine ES threshold membership is not pinned

- File: `backend/tests/test_var_es_golden.py`
- What's wrong: The only discriminating `>=` versus `>` test calls `VaRAnalytics` at 95%. No case makes `HistoricalRiskEngine.expected_shortfall_99` differ under strict-`>` membership.
- Why it matters: Mutating `HistoricalRiskEngine` from `losses >= var99` to `losses > var99` still passes all current goldens. Cases A, D, F, and G have interpolated thresholds below the maximum; E falls back to the same VaR; B/C also produce the same result.
- Suggested fix: Add an engine-level distribution with 101 losses `0..100`. Hand values are VaR99 `99` and ES99 `(99 + 100) / 2 = 99.5`; strict `>` incorrectly gives `100`.

### 3. VALID — Important — Full-revaluation engine routing can silently regress

- File: `backend/tests/test_full_reval_golden.py`
- What's wrong: `test_historical_engine_full_reval_matches_explicit_pv_difference` uses a linear equity and derives expected VaR with `np.quantile` from the production helper. For this trade, LINEAR and FULL_REVALUATION P&L are identical, so an engine mutation that routes FULL_REVALUATION through the linear path can pass.
- Why it matters: The direct helper has a good literal P&L assertion, but the orchestration test does not prove `HistoricalRiskEngine` actually selected pricing-driven full revaluation.
- Suggested fix: Use a nonlinear trade with hand/toleranced shocked PVs, or inject a recording pricing engine whose shocked-market calls can be asserted. Keep VaR expectations literal rather than recomputing them with `np.quantile`.

### 4. VALID — Important — Key-rate DV01 is not an exact hand golden

- File: `backend/tests/test_approx_pnl_units_golden.py`
- What's wrong: The key-rate test compares one production finite difference with another production pricing difference, allowing 5% and 15% bands. It does not pin a literal key-rate DV01 or exact one-bp P&L.
- Why it matters: This is weaker than the R0.1.3 “exact one-factor” unit bar and can hide correlated defects in bumping and valuation. The broad 100bp linearization check is also not a clean unit golden.
- Suggested fix: Use the builtin linear swap formula at one attached tenor. Its hand value is `sign * notional * duration * 0.0001` per bp, and a +1bp key-rate shock has exactly that P&L. Assert tenor isolation and literal values tightly.

### 5. VALID — Minor — Snapshot-as-of test cannot detect the claimed contract

- File: `backend/tests/test_quantlib_process_state.py`
- What's wrong: The test compares two zero-coupon bond PVs that are expected to be equal because maturity is expressed as years from evaluation and the curve is flat. It would still pass if `snapshot.as_of` started driving the QuantLib date.
- Why it matters: The docstring says a silent semantic flip will be visible, but this assertion cannot make it visible.
- Suggested fix: Observe `Settings.evaluationDate` inside a controlled pricing/session seam, or use a date-sensitive contractual instrument once explicit maturities exist. Until then, make this documentation-only limitation explicit rather than claiming the PV assertion pins date ownership.

### 6. VALID — Minor — “Rejects mutation” tests are tautological

- File: `backend/tests/test_var_es_golden.py`
- What's wrong: The two rejection tests calculate known-wrong standalone numbers and assert they differ from literals. They never call a mutated engine and add no protection beyond the functional golden cases.
- Why it matters: Assertions such as “wrong-tail result is not 19.05” can keep passing even when production is changed to that wrong tail.
- Suggested fix: Rely on the engine-facing literal goldens, or add a small mutation test/harness that substitutes the quantile/tail operation and proves the engine-facing assertions fail.

### 7. VALID — Minor — Fixing-history test is order-dependent

- File: `backend/tests/test_quantlib_process_state.py`
- What's wrong: `test_swap_valuation_leaves_ibor_fixings_in_process` only asserts that at least one global history exists after valuation. It neither clears nor snapshots pre-existing process state.
- Why it matters: In the full suite, prior QuantLib tests can leave histories behind, so removing fixing seeding from this valuation may not fail this test.
- Suggested fix: Isolate the global state with `IndexManager.clearHistories()` in a `try/finally`, then assert the specific expected history/fixing was added and restore/clear afterward.
