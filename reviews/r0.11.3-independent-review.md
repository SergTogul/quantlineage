## Verdict: REVISE

The app-level dependency is real, dual-mounted, and I verified the five
acceptance checks against source and HTTP, not from the implementer report.
That is not enough to approve the slice. SEC-002 is an availability finding
about unbounded client-controlled work and memory. Two holes leave that
control hollow on live paths:

1. `POST /risk/what-if` computes a book grown by `changes[].position` while
   the inspector only looks at lists named `positions`. With
   `QUANTLINEAGE_MAX_POSITIONS=2` a 1-position book plus 3 adds returned **200**
   and `after.market_value=400` (four equities).
2. Missing `Content-Length` (chunked / streaming) is fully buffered by
   `await request.body()` before the byte cap runs. An ASGI probe with
   `QUANTLINEAGE_MAX_REQUEST_BYTES=64` delivered all 245 bytes in five receive
   events, then 413. A streaming reject would have stopped after the first
   80-byte chunk.

The implementer listed both as known limitations. They are still defects
against this slice: the position cap is not a computed-book cap, and the
body cap does not protect memory when the client omits `Content-Length`.

## Findings

### 1. VALID — Important — What-if `add` bypasses the position cap

- Files: `backend/app/api/workload.py` (`enforce_parsed_payload`,
  `_named_list_lengths`), `backend/app/domain/models.py` (`WhatIfRequest`,
  `WhatIfChange`), `backend/app/api/risk.py` (`POST /risk/what-if`).
- What's wrong: Caps apply only to JSON lists named `positions` or
  `scenarios` (plus a top-level array as scenarios). `WhatIfChange.position`
  is a singular object inside `changes`. A client sends a legal
  `positions` list and an arbitrary number of `add` ops. The inspector
  never sees an oversize `positions` list. The route then runs incremental
  VaR / stress on the mutated book.
- Why it matters: SEC-002 is about client-controlled books forcing expensive
  work. `QUANTLINEAGE_MAX_POSITIONS` is the operator control for that. It does
  not bind the computed book on a live risk route.

  | Probe | Result |
  |---|---|
  | `MAX_POSITIONS=2`, portfolio 1 equity, 3 `add`s, `POST /api/v1/risk/what-if` | **200** |
  | `after.market_value` | **400.0** (four × 100, not one) |

  One change is ~117 JSON bytes. Default 1 MiB allows on the order of
  **8k adds**. Tightening only `QUANTLINEAGE_MAX_POSITIONS` (e.g. to 50) does
  not close this. Body size is a different knob and still permits a
  multiple of the documented position cap.
- Suggested fix: Count work that becomes a position, not only the key
  `positions`. Practical options: (a) for each object that has both
  `positions` and `changes`, reject when
  `len(positions) + count(add with position) > max_positions`; (b) treat a
  `changes` list longer than `max_positions` as oversize *and* apply (a).
  Add an HTTP test that 1 + (cap+1) adds is 413. Do not leave this to
  `risk.py` (forbidden) when the inspector can see the wire shape.

### 2. VALID — Important — Body cap buffers the full stream when `Content-Length` is omitted

- File: `backend/app/api/workload.py` (`enforce_workload_limits`)
- What's wrong:

  ```python
  if content_length is not None:
      ...
      if declared > byte_limit:
          _raise_body_too_large(...)
  if request.method not in {"POST", "PUT", "PATCH"}:
      return
  body = await request.body()          # unbounded read
  if len(body) > byte_limit:
      _raise_body_too_large(...)
  ```

  The early reject works only when `Content-Length` is present and honest.
  Chunked HTTP/1.1 and any ASGI client that omits the header skip it.
  `Request.body()` accumulates the entire stream, then checks `len`.
  That is the memory DoS the byte cap exists to stop (SEC-002 / CWE-770).
  Starlette JSON parsing would also buffer — but only for requests that
  *proceed*. Oversize requests should never become a `bytes` of attacker
  length.
- Why it matters: Raw ASGI, `QUANTLINEAGE_MAX_REQUEST_BYTES=64`, no
  `Content-Length`, body 245 bytes in 80-byte chunks:

  | Case | Receive log | Status |
  |---|---|---|
  | Declared `Content-Length: 999999`, no body | `[(0, False)]` | 413 `actual=999999` |
  | No CL, one-shot 245 B | `[(245, True), (0, False)]` | 413 `actual=245` |
  | No CL, 80+80+80+5 | **five** events, all chunks delivered | 413 `actual=245` |

  A running-total stream abort would stop after the first 80-byte chunk
  (`80 > 64`) and would not retain the rest. TestClient/httpx normally
  send `Content-Length`, so `test_oversized_request_body_rejected` never
  exercises this path. The implementer documented the gap; it is still
  the primary body-size control failing on the attack that omits the
  header.
- Suggested fix: Do not call `request.body()` until the size is known to
  be `<=` the cap. Stream `request.stream()` (or wrap ASGI `receive`) with
  a running total; on overflow raise 413 and stop iterating without
  keeping the tail. Keep the `Content-Length` pre-check. Add an ASGI or
  chunked-body test that would fail if `request.body()` is used first.

### 3. VALID — Minor — Recursive payload walk `RecursionError`s on deep JSON under the byte cap

- File: `backend/app/api/workload.py` (`_named_list_lengths`)
- What's wrong: The walker is unbounded recursion over every dict/list
  child. `json.loads` accepts a 7 KB 1200-deep `{"a":{"a":...}}` object.
  The new inspector then blows the Python stack.
- Why it matters: `TestClient(..., raise_server_exceptions=False)` returned
  **500** `{code: internal_error, ...}` — not 413/422. The unhandled
  handler logs `maximum recursion depth exceeded` with a ~1000-frame
  traceback. This is a robustness hole introduced by this slice, not a
  compute-scale bypass (payload is tiny). Uvicorn typically turns it into
  500 rather than killing the worker.
- Suggested fix: Iterative walk with a small max depth (or reject past
  depth with 413/422). Add a test that a deep object under the byte cap
  is not 500.

### 4. VALID — Minor — Position cap is per named list, not per request

- File: `backend/app/api/workload.py` (`enforce_parsed_payload`)
- What's wrong: Each `positions` list is compared to the cap independently.
  `previous_portfolio` + `current_portfolio` at 2+2 with
  `MAX_POSITIONS=2` is allowed; attribution returned **200**. 3+1 is 413.
- Why it matters: Attribution, risk-change, and hedge-compare price two
  books. Worst case is `2 × max_positions` (plus scenarios), not unbounded.
  Body size still bounds how many stub lists fit. Weaker than Finding 1;
  not a what-if-scale hole.
- Suggested fix: Optionally sum `positions` list lengths per request, or
  document that dual-portfolio routes may do `2 ×` the cap. Not required
  to close Finding 1 if what-if adds are counted.

### 5. VALID — Minor — Tests pin defaults and list-key HTTP 413, not the holes above

- File: `backend/tests/test_workload_limits.py`
- What's wrong: No what-if add case, no chunked/missing-`Content-Length`
  case, no deep-JSON case, no assertion that `app.router.dependencies`
  contains `enforce_workload_limits` (HTTP 413 is the real pin and is
  enough for acceptance #4).
- Why it matters: Findings 1–2 can ship while this file stays green.
  Raising `DEFAULT_MAX_*` or deleting the `Depends(...)` would still fail.
- Suggested fix: One HTTP what-if add over cap; one ASGI/chunked body
  over cap that would fail if the implementation buffers first.

## What is not a finding

- Nested portfolios under a `positions` key **are** counted. The hunt
  item “nested portfolios not counted” is closed for that shape.
- Dual-mount coverage: app-level `Depends` applies to domain routers and
  `risk_runs_router` at both prefixes. Probed.
- 413 envelope mismatch: none. Structured `error_payload` yields
  `payload_too_large`, not `http_413`.
- GET/health: not blocked. Huge query strings are not a compute path.
- `SAMPLE_PORTFOLIO` (9 names) is under default caps.
- Observation query `le=5000` on `/risk/var/compare` and reverse-stress
  iteration default 40: listed on the broad R0.11.3 plan, not on this
  review’s acceptance list; compare is already bounded; `/var` and `/es`
  use the server dataset. Queue depth is a later slice.
- DI-supplied default scenario lists when the client omits `scenarios`:
  server-owned, not a client bypass.
- Calling `request.body()` on in-cap POSTs (double parse): harmless;
  Starlette caches the body for the route.

## Strengths

- Single app-level dependency avoids editing forbidden routers and does
  cover legacy + `/api/v1` risk, limits, runs, stress, and market.
- `Content-Length` pre-check is correct when the header is present:
  413 with `actual` equal to the declared size and no body consume.
- Rejection shape is the existing `{code, message, details}` envelope
  with `field` / `limit` / `actual`.
- Env is read per request; non-positive / invalid values fall back to
  defaults instead of disabling the cap.
- Inclusive boundary (`exactly max` allowed) is tested and holds.
- HTTP tests would catch a removed `Depends` or a raised `DEFAULT_*`.
