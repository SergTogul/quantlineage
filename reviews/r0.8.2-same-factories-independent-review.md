### 1. VALID — Minor — Factory-sharing tests lock the import, not the `deps` call

- What I observed: `test_deps_and_worker_use_same_factory_callable` asserts `deps.build_portfolio_service is build_portfolio_service` (same imported function object). `test_worker_main_constructs_via_shared_factory` only greps `worker.main` source. Neither inspects `deps.portfolio_service.risk.dataset`. A mutation that kept the import and restored `PortfolioService(create_pricing_engine(), HistoricalRiskEngine())` in `deps.py` would stay green on those two tests.
- Why it matters: that mutation would reopen API-interactive vs Compose-worker dataset drift — the RF-009 construction bug — without failing the “same factory” tests.
- Suggested fix: assert `deps.portfolio_service.risk.dataset` is the factory demo `FileHistoricalDataset` (`dataset_id == "demo-historical-factors"`), or grep/assign that `portfolio_service = build_portfolio_service()` appears in `deps.py`. Not required to APPROVE this slice; production already calls the factory (probe above).

### 2. VALID — Minor — HTTP create-run test does not pin factory identity or reload

- What I observed: `test_create_persists_factory_dataset_identity` asserts `historical_dataset_id` / `version` `is not None` on the 202 body. It sends request `as_of` / `calculation_config`, so those fields are request overrides, not factory-derived. It does not GET the run or load a repository row. A synthetic-default engine would still satisfy `is not None` (`synthetic-historical-factors` / `v1`).
- Why it matters: the test name claims factory identity; the lock is “some spec leaked into the 202 JSON.”
- Suggested fix: pin `demo-historical-factors` / `v1` (or the live `resolve_run_spec` of `deps.portfolio_service.risk`) and GET `/risk/runs/{id}`. Stronger persist locks already exist in `test_risk_run_spec.py` (`test_enqueue_persists_explicit_spec_fields`, `test_submit_with_request_spec_persists_columns`, `test_submit_without_request_spec_records_factory_dataset`).
