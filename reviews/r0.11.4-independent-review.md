### 1. VALID — Minor — Drilldown 400 has no mutation lock

- Files: `backend/tests/test_error_sanitization.py`, `backend/app/api/limits.py`
- What's wrong: The leaky-override test covers `POST /risk/what-if` only. Create-run is locked by asserting `unsupported run_type` / `not-a-real-type` are absent. Every drilldown HTTP test I found is the 200 path (`test_api_limits_drilldown`, typed-models, v1 compatibility).
- Why it matters: A one-line revert of `limits.py` to `HTTPException(..., detail=str(exc))` would not fail the new sanitization suite. I confirmed the live handler *is* sanitized; this is a missing lock, not a live leak.
- Suggested fix: Copy the what-if leaky-service test onto `POST /risk/limits/drilldown` (and `/api/v1/...` if you want dual-mount parity).

### 2. VALID — Minor — FAILED GET is not asserted over HTTP

- Files: `backend/tests/test_error_sanitization.py`, `backend/tests/test_risk_run_api.py`
- What's wrong: SEC-008 asked for a GET `/risk/runs/{id}` FAILED body test parallel to `test_m75_unhandled_500_shape`. Both new tests call `worker.get()` only.
- Why it matters: `RiskRunView` has a single `error_message` field and GET is a thin wrapper, so a worker-side `str(exc)` revert *would* fail today's tests. A later HTTP-only transform would not. My GET probe was clean (`error_message=Risk run failed`, no sibling `error` key, leak text absent).
- Suggested fix: After a forced failure, assert the GET JSON (legacy and `/api/v1`) equals the public constant and fails the leak needles.

### 3. VALID — Minor — Sanitization is call-site / write-site only

- Files: `backend/app/api/errors.py` (`body_from_http_exception` L93–96), `backend/app/domain/models.py` (`RiskRunView.from_risk_run`), `backend/app/services/risk_run_worker.py` L275–276, L312–314
- What's wrong: String `HTTPException.detail` is still copied into `message`. GET returns whatever was persisted. `svc.fail` still accepts any non-empty string. Remaining writers that are *not* `str(exc)`:
  - `portfolio {pid!r} missing for queued run`
  - `portfolio payload missing for run`
- Why it matters: Pre-slice FAILED rows in a durable DB, or a future `fail(run_id, str(exc))`, would still be public. Controlled missing-portfolio copy can echo a client `portfolio_id`; that is not QuantLib/traceback leakage. The handler will also happily re-publish a new `detail=str(exc)` if someone adds one.
- Suggested fix: Keep the stable worker constant. Optionally map GET `error_message` through an allow-list, and/or refuse string `detail` on 400 unless it is already a structured `{code,message,details}` payload.

### 4. VALID — Minor — Worker imports the HTTP error module

- File: `backend/app/services/risk_run_worker.py` L23
- What's wrong: `RiskRunWorker` imports `PUBLIC_RISK_RUN_FAILURE_MESSAGE` from `app.api.errors`. Implementer noted this.
- Why it matters: No cycle today (`errors.py` does not import the worker). It does invert the usual service → API direction and pulls FastAPI into any `python -m app.worker` import of the worker module.
- Suggested fix: Move the two public-copy constants to domain or a tiny shared module.

Worker logging vs public string: **not mixed up.** `_execute` logs `logger.exception("risk run failed: %s", run_id)` (traceback server-side) and persists the public constant. `http_bad_request` logs `logger.exception` with the real `exc` and returns `Invalid request`. Operators can still tell a missing position from a QuantLib `ValueError` in logs. Over-sanitizing the 400 message is therefore acceptable for this slice. Current UI `api.js` does not surface the 400 envelope anyway (`${status} ${statusText}`); FAILED `error_message` *is* shown in `Analytics.jsx` and will now be `Risk run failed`.
