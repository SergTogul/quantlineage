## Findings

### 1. VALID — Important — Tree uniqueness is not structural; raw trade `id` collides in legal books

- Files: `backend/app/risk/hierarchy_placement.py` L13–35 (`return trade_id or "trade"`; PORTFOLIO returns raw `portfolio_id`); `backend/app/risk/hierarchy.py` L228–236; `backend/tests/test_hierarchy_node_ids.py` L183–213
- What's wrong: The report claims ids are unique in a multi-desk / multi-book tree. The helper copies the old `portfolio_at` strings, including unprefixed trade ids. `Portfolio.unique_ids` only forbids duplicate **position** ids. It does not make `HierarchyNode.id` unique across levels, and the `or "trade"` / `or "book"` fallbacks alias distinct labels onto one key. In-memory `HierarchyEngine.build` on legal books (no production edits):

  | Book | Duplicate `id` |
  |---|---|
  | `Portfolio(id="eq-a")` + trade `eq-a` (and `eq-b`) | `eq-a` on portfolio **and** trade |
  | position `id=""` under Cash A, `id="trade"` under Cash B | `trade` on **both trades** |
  | trade `id="desk:Rates Desk"` | `desk:Rates Desk` on desk **and** trade |
  | books `""` and `"book"` under the same desk/strategy | `book:D/S/book` on **both book** nodes |

  `test_ids_unique_in_multi_desk_multi_book_tree` and
  `test_trades_under_different_books_do_not_collide` use `portfolio.id="multi-desk"`
  and distinct `eq-*` ids. They stay green for every row above.
- Why it matters: R0.7.3 / RF-008 will “evaluate limits against explicit
  stable hierarchy-node IDs.” A limits or drilldown key of `eq-a` is
  ambiguous in a legal book whose portfolio id is also `eq-a`. Matching
  `portfolio_at` is not a uniqueness proof — `portfolio_at` on that book
  returns `eq-a` for both PORTFOLIO and TRADE refs. The implementer
  limitation note only mentions two copies of the same trade id (already
  illegal) and future multi-portfolio desks. It does not mention these
  live collisions.
- Suggested fix: Namespace every level in `hierarchy_node_id` (including
  `portfolio:{portfolio_id}` and
  `trade:{desk}/{strategy}/{book}/{trade_id}`). Drop falsy fallbacks that
  map `""` / `None` onto the literals `"trade"` and `"book"`. Keep
  `portfolio_at` on the same helper so the address space stays one
  scheme — that is an intentional `Portfolio.id` change at trade /
  portfolio subset level and needs a consumer check. Add tests that the
  four legal books in the table above produce `len(ids) == len(set(ids))`
  and nonempty ids. Do not weaken 1e-9 goldens to do this.

### 2. VALID — Minor — Engine-built portfolio node can have empty `id`

- Files: `backend/app/risk/hierarchy_placement.py` L27–29;
  `backend/app/domain/models.py` L1290; `backend/tests/test_hierarchy.py`
  L206–221 (`test_empty_portfolio_zero_risk_tree` does not assert ids)
- What's wrong: `hierarchy_node_id("portfolio", …)` returns `portfolio_id`
  with no prefix and no nonempty check. `Portfolio.id: str` has no
  `min_length`. Probe: `Portfolio(id="", …)` builds
  `[('firm', 'firm:Acme'), ('portfolio', ''), …]`.
- Why it matters: The report says the engine always populates `id`. It
  populates the field with `""` when the book id is empty. Attack 1 is
  live for that book. Demo ids (`multi-desk`, `global-macro`) are fine.
- Suggested fix: Covered by Finding 1’s `portfolio:{…}` namespace plus a
  nonempty assert (or `Field(min_length=1)` on `Portfolio.id` if Lead
  Architect wants that invariant). Assert ids on the empty-book tree test.

### 3. VALID — Minor — Slash-delimited strategy/book ids are ambiguous

- File: `backend/app/risk/hierarchy_placement.py` L31–34
- What's wrong: `strategy:{desk}/{strategy}` (and the book triple) cannot
  distinguish desk=`Rates/Extra` + strategy=`Carry` from desk=`Rates` +
  strategy=`Extra/Carry`. Probe: both helpers return
  `strategy:Rates/Extra/Carry`. There is no validation that desk /
  strategy / book labels lack `/`.
- Why it matters: `path` already uses `/` as breadcrumb, so display was
  already ambiguous. `id` was supposed to be the stable address. Same
  delimiter without encoding re-imports the ambiguity into the key.
- Suggested fix: Encode path segments (or use a separator that labels
  cannot contain) when namespacing in Finding 1. Not a current-demo
  collision (`Rates Desk` / `Carry` have no slashes).
