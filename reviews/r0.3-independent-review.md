## Verdict: REQUEST CHANGES

The adapter lock, `_session` boundary, outermost `IndexManager` clear, and
Acc 5 overlap test are real. I reproduced the per-instance `RLock` mutation
in memory: `b_entered_while_a_inside` becomes true and the overlap test fails.

The as-of claim does **not** hold on the default application path.
`create_pricing_engine()` wraps `QuantLibPricingEngine` in `CachedPricingEngine`,
and `market_cache_key` / `MarketSnapshot.content_hash()` omit `as_of`. Two
snapshots with identical marks and different ISO dates share one key. I priced
the same 2Y USDLibor swap through the factory: after a `2018-01-01` miss, a
`2024-06-14` hit returned the 2018 PV (`102212.08…`) instead of the unwrapped
2024 PV (`102200.05…`). That is a leftover as-of bypass created by this slice
making `as_of` load-bearing while the cache still treats it as a label.

Do **not** close RF-002.

## Findings

### 1. VALID — Important — Default factory cache ignores parseable `as_of`

- Files: `backend/app/pricing/cache.py:109-113`, `backend/app/pricing/cache.py:178-191`,
  `backend/app/domain/models.py:733-734`, `backend/app/pricing/factory.py:36-47`
- What's wrong: This slice makes ISO `as_of` drive QuantLib evaluation date and
  calendar-sensitive instruments. `CachedPricingEngine` is on by default and
  keys only `content_hash()` plus a constructor `evaluation_date` frozen at wrap
  time. `as_of` is excluded as a “label.” Two ISO dates with the same marks
  collide. The process-state as-of test calls the unwrapped engine, so it stays
  green.
- Why it matters: I ran `create_pricing_engine()` (cache on, inner
  `QuantLibPricingEngine`) on one 2Y payer swap, marks `rates={"USD": 0.04}`:

  | Path | `as_of=2018-01-01` | `as_of=2024-06-14` |
  |---|---|---|
  | Unwrapped engine | 102212.08381212864 | 102200.05429597793 |
  | Factory, 2018 then 2024 | 102212.08381212864 | **102212.08381212864** (hit) |

  ZCB PVs were identical across dates (years-from-eval), which is why a bond
  spy is a weak factory probe. The swap calendar/fixing path is not. R0.2.4
  already required as-of in the cache key; this slice made that omission a
  wrong-PV bug rather than a dormant identity gap.
- Suggested fix: Put parseable `as_of` (or the session evaluation date) into
  `market_cache_key` / `content_hash` or `PricingConfiguration` per call so
  different ISO dates cannot hit. Add a factory-level test that the 2018 then
  2024 swap order returns the unwrapped 2024 PV. This is not R0.3.1 (typing)
  and not R0.3.5 (process partitions).

### 2. VALID — Minor — Acc 5 window can miss a late second thread

- File: `backend/tests/test_quantlib_process_state.py:95`
- What's wrong: A sleeps 0.2 s after entering. If B’s thread does not reach
  `b._session()` before A samples, `b_entered_before_a_sampled` stays unset
  and the mutation can pass.
- Why it matters: On this host the mutation failed as required. A loaded CI
  worker could theoretically hide a lock regression. The entry assertion is
  the right one; the sleep is the weak part.
- Suggested fix: Event-gate B’s lock acquire (or raise the wait until A
  samples) so B cannot miss the window.

### 3. VALID — Minor — Nested no-clear and exception-restore are untested

- File: `backend/tests/test_quantlib_process_state.py` (missing cases)
- What's wrong: Depth/clear-on-outermost-only and Settings restore after a
  failed `value()` are implemented and worked in probes; nothing in the suite
  pins them. A “clear on every enter” mutation would still pass the current
  swap tests (production `value()` is a single outermost session).
- Why it matters: The implementer claimed nested same-thread sessions do not
  clear mid-valuation. That claim is true in code, not in tests.
- Suggested fix: One nested `_session` test that histories survive the inner
  enter, and one `value()` that raises inside `_bond` and asserts Settings /
  depth / `evaluation_date` after the exception.

### 4. VALID — Minor — `YYYY-MM-DDTHH:MM:SS` is treated as a label

- File: `backend/app/pricing/quantlib.py:49-61`
- What's wrong: `date.fromisoformat("2018-01-01T00:00:00")` raises here, so
  the parser returns `None` and the engine date wins. `datetime` instances
  pass the `isinstance(as_of, date)` branch and are stored as datetimes.
- Why it matters: The written contract is calendar `YYYY-MM-DD` / `date`,
  which works. Persistence and goldens already use date-only strings or
  labels. Full ISO datetimes would silently stay on wall-clock/engine date.
- Suggested fix: Either accept a leading `YYYY-MM-DD` prefix, or keep the
  narrow parser and state that datetime forms are labels until R0.3.1.

### 5. VALID — Minor — Docs still describe the pre-R0.3 lock

- Files: `docs/known_limitations.md:52`, `docs/adr/007-quantlib-concurrency.md:31-33`
- What's wrong: Known limitations still say the adapter lock is per-instance
  and overlapping sessions can contaminate evaluation dates. ADR 007 still
  says each engine owns an instance `RLock`.
- Why it matters: RF-020 treats `docs/known_limitations.md` as the truth
  source. It now contradicts the adapter. Not a runtime defect.
- Suggested fix: Update the limitation to “in-process QuantLib is serialized
  by `_QL_PROCESS_LOCK`; cache keys must include as-of; parallel full reval
  is process-partitioned (R0.3.5).” Leave RF-002 open.

## Strengths

- Process lock is module-owned and bound in `__init__`; two instances share
  one object (`a._lock is b._lock is _QL_PROCESS_LOCK`).
- `_session` is the only Settings / IndexManager writer in production pricing
  code. Depth + outermost clear is the right shape for 1.43 Python bindings.
- Acc 5 asserts interleaving entry, not only the observed date. Restoring
  `self._lock = RLock()` in memory fails that test.
- Unwrapped `value()` honors `YYYY-MM-DD` and leaves labels on the engine
  date. Goldens keep `as_of="current"` and did not need tolerance changes.
- RF-002 is still IN PROGRESS with R0.3.1 / R0.3.5 listed as remaining.
  The implementer did not claim those slices done.
