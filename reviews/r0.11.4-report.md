# R0.11.4 Error sanitization

## Task
R0.11.4 Error sanitization (RF-014)

## Owner
Backend / API Engineer

## Summary
Failed risk HTTP responses no longer return `detail=str(exc)`. `POST /risk/what-if`, `POST /risk/limits/drilldown`, and `POST /risk/runs` now raise a structured `{code,message,details}` 400 with the stable message `Invalid request`, and the original exception is logged server-side. Unhandled 500s remain the existing opaque `internal_error` body. FAILED risk-run persistence now stores the public string `Risk run failed` instead of `str(exc)` / exception class names.

TDD: `tests/test_error_sanitization.py` was written first and failed (what-if leaked `QuantLib::Error` / file path; risk-run `error_message` stored the raw `RuntimeError`). Implementation then turned those tests green.

## Public/interface changes
- Client-visible 400 message for caught `ValueError` on what-if, limit drill-down, and risk-run create is now `Invalid request` (`code=bad_request`). Raw exception text (including previously echoed `unsupported run_type …`) is not returned.
- FAILED risk-run public field `error_message` is now `Risk run failed` instead of the underlying exception string.
- OpenAPI `EXAMPLE_BAD_REQUEST.message` updated to `Invalid request`.
- Envelope shape `{code,message,details}` is unchanged. Unhandled 500 body is unchanged (`internal_error` / `An unexpected error occurred`).

## Known limitations / risks
- Domain `ValueError` text (e.g. missing position, unsupported run type) is no longer shown to clients; operators must use server logs.
- Controlled worker strings such as `portfolio payload missing for run` are unchanged (they are not `str(exc)`).
- `RiskRunWorker` imports the public failure constant from `app.api.errors` (sanitization policy lives with the HTTP error model).
- Parallel R0.2-A work can raise `ConflictingSampleMarkError` on some what-if *success* paths (`test_what_if.py` add/remove helpers). Those files were not edited here; that failure is outside this slice.
