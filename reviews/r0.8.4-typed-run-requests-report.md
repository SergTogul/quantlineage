R0.8.4 — Typed RiskRun request schemas (discriminated by run_type)

## Owner
Backend / API Engineer

## Summary
Replaced opaque RiskRun `request: dict[str, Any]` blobs with typed Pydantic bodies (`RiskRunRequestBody` and per-`run_type` aliases) using `extra='forbid'`. `RiskRunCreateRequest` and `RiskRunWorker.submit` both validate through `parse_risk_run_request`; the JSON dump is what persistence and execution see. Client-supplied `historical_dataset_id` rebinds the historical engine via shared factory helpers (`resolve_dataset_source`, `build_historical_risk_engine`, `portfolio_service_for_spec`) for both resolve and worker execution, or raises (HTTP 400) when unsupported — it is never stored as a label while another dataset runs. CSV-backed datasets use path-derived ids (`file:<abspath>`) so distinct paths rebind correctly; bare `"file"` and missing CSVs fail 400. Invalid methodology / unknown request keys fail 422 at create. RF-009 remains open for R0.8.5; this slice awaits independent re-review after Important #1.

## Fix note (Important #1 — CSV identity collapse)

Independent review CHANGES REQUESTED: all CSV loads defaulted `dataset_id="file"`, so `portfolio_service_for_spec` could silently keep process CSV A when the request asked for CSV B.

Fix: `file_csv_dataset_id` → canonical `file:<resolved-abspath>`; `load_csv_historical_dataset` / `create_historical_dataset` set that id (demo/synthetic aliases unchanged). `resolve_dataset_source` requires an existing file, accepts `file:<abspath>`, and rejects ambiguous bare `"file"` with ValueError → HTTP 400. Missing `*.csv` paths also 400 (not 500). Tests cover A→B rebind, bare `"file"`, and missing CSV.
